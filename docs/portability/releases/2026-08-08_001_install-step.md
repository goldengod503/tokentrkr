# 2026-08-08 — `just install`: stop symlinking the installed applet into `target/`

## Summary

`~/.local/bin/tokentrkr` was a symlink into `target/release/tokentrkr`, which
made the installed panel applet an alias for whatever the build tree last
produced. Added `just install` (and `just build-sni`), repointed `just restart`
at it, and replaced the symlink with a real copy. Documentation-and-tooling
change only — no Rust source touched, no behavior change in either build target.

## Context

Found while confirming it was safe to reboot after the applet-lifecycle fixes
(`43c635c`). Those were briefly tagged v0.9.1; the tag and release were
withdrawn the same day as no-user-impact, and the commits ship in the next
release. `~/.local/bin` was
audited for symlinks pointing into build directories; `tokentrkr` was the only
one on the system. `~/.local/bin/galaxy-systrkr` — the other COSMIC applet on
this machine — was already a real binary copy, so the symlink was the outlier,
not the convention.

Two concrete failure modes, both silent:

1. **Target swap.** Both build targets write the same path. `cargo build
   --release` produces the COSMIC applet (28,982,008 bytes); `cargo build
   --release --no-default-features` produces the SNI tray (9,415,960 bytes).
   With a symlink, running `just build-sni` to check the SNI path replaces the
   panel applet with a tray binary at the next panel restart. Nothing warns.
2. **`cargo clean`.** Removes `target/`, leaving `~/.local/bin/tokentrkr` a
   dangling symlink and the panel applet unlaunchable.

Neither had fired yet. This is prevention, not a fix for observed breakage.

## Behavioral Impact

No user-visible behavior change in either build target. No Rust source modified.

The installed applet is now decoupled from the build tree: `cargo build`,
`cargo clean`, and branch switches no longer change what the panel launches.
Picking up a new build is now an explicit `just install`.

`install` (GNU coreutils) unlinks the destination before writing, so it succeeds
while the applet is running — unlike `cp`, which fails with `ETXTBSY`. The
running process keeps its old inode until the panel restarts it.

`just --list` doc comments are single-line by necessity: `just` takes only the
**last** comment line before a recipe as its description, so multi-line comments
render as fragments.

## Open Questions / Decisions

### Decision: install to `~/.local`, not `/usr`

- **Status**: Accepted
- **Date**: 2026-08-08
- **Context**: The README previously documented `sudo cp` to `/usr/bin` and
  `/usr/share/applications/`, but the desktop entry actually in use on this
  machine lives at `~/.local/share/applications/`. Docs and reality disagreed.
- **Decision**: `just install` targets `~/.local/bin` and
  `~/.local/share/applications`. System-wide install is mentioned in the README
  as an alternative, unautomated.
- **Consequences**: No `sudo` in the default install path, so `just install` and
  `just restart` run unprivileged. Requires `~/.local/bin` on `PATH` for the
  entry's `Exec=tokentrkr` to resolve — true by default on Pop!_OS.
